# 전공과 공공 분야를 연결하는 프로젝트

처음에는 아래 중 하나만 선택한다. 데이터 이용조건을 확인하고 공개·비식별 자료나 합성 데이터로 시작한다. 아래는 과제 설계이며 이미 구현·검증한 서비스나 성능 결과가 아니다.

## 프로젝트 A: 공공데이터 수요 예측

예시 문제: 날짜별 공개 이용량으로 다음 날 이용량을 예측한다. 데이터셋 선택 전 날짜 범위·누락·갱신 주기·이용조건을 확인한다.

- 입력: 예측 시점에 이용 가능한 과거 이용량·달력 특성.
- 타깃: 다음 날 이용량. 미래의 실제 관측값을 특성에 넣지 않는다.
- 분할: 시간순 훈련·검증·테스트. 중복 기록과 시간 역전을 확인한다.
- 기준모델: 전일값 또는 전주 같은 요일 값.
- 비교모델: 선형회귀와 트리 계열 하나.
- 평가: MAE·RMSE, 평일/주말 오류, 큰 오차 사례.
- 보고서: 데이터 범위, 기준모델 대비 개선, 수요 변화 시 한계, 재학습 판단 기준.

완료 기준: 동일 데이터·설정으로 재현 가능하고 기준모델보다 못한 경우도 그대로 보고한다.

## 프로젝트 B: 공개 민원 예시 분류

예시 문제: 개인정보가 없는 공개·합성 문장을 교통·환경·복지 등 미리 정한 범주로 분류한다. 실제 민원 원문을 무단 수집하지 않는다.

- 데이터: 범주 정의와 라벨 기준을 먼저 작성한다.
- 분할: 유사 문구·중복 문서가 훈련과 테스트에 나뉘지 않도록 그룹화한다.
- 기준모델: TF-IDF + 선형 분류기.
- 확장: 작은 사전학습 모델과 비교하되 비용·지연도 기록한다.
- 평가: macro-F1, 클래스별 precision·recall, 혼동행렬.
- 오류 분석: 두 범주에 걸친 문장, 짧은 문장, 분포 밖 문장.
- 공공 업무 관점: 낮은 확신 또는 모호한 문장은 사람에게 검토를 넘기는 흐름을 설계한다.

완료 기준: 단일 정확도 외에 범주별 실패 사례와 라벨의 한계를 설명한다. 사람에 대한 불이익 결정을 자동화하는 프로젝트로 확대하지 않는다.

## 프로젝트 C: 공개 문서 검색·질의응답

예시 문제: 이용 가능한 공개 안내문 몇 개에서 근거 문단과 함께 답한다.

- 먼저 키워드 검색 기준모델을 만든다.
- 문서의 제목·버전·날짜·문단 위치를 보존한다.
- 임베딩 검색을 비교하고 필요하면 생성 단계를 추가한다.
- 자체 질문 세트에 정답 근거 문단을 연결한다.
- 검색 recall@k, 답변 정확성, 인용 근거 일치, 답이 없는 질문 처리, 지연을 측정한다.
- 문서의 명령문이 도구 실행이나 권한 변경으로 이어지지 않게 설계한다.

완료 기준: 답변마다 근거 위치를 보여주고 문서에 답이 없으면 한계를 표시한다. RAG라는 이유만으로 정확하다고 주장하지 않는다.

## 공통 제출 구조

```text
project/
  README.md        # 문제, 실행 방법, 데이터 출처
  data/README.md   # 다운로드 방법과 이용조건, 원본은 필요시 제외
  src/            # 전처리·학습·평가 코드
  results/        # 지표·오류 분석
  report.md       # 해석과 한계
```

보고서는 ‘무엇을 예측·검색하는가 → 어떤 데이터인가 → 어떻게 나눴는가 → 무엇과 비교했는가 → 얼마나 틀렸는가 → 어디에 쓸 수 있는가’ 순서로 쓴다. 성능 수치를 만들거나 검증 결과를 예상값으로 채우지 않는다.
