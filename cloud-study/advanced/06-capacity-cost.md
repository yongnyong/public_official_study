# 6장. 성능·용량·비용을 계산으로 설명하기

[목차](README.md)

모든 단가는 가상이며 실제 AWS 가격이 아니다. 계산은 가정을 이해하기 위한 예제다. 평균값의 단순 산술을 실제 SLA 보장으로 사용하지 않는다.

## 1. 동시 처리 수

안정 상태에서 Little's Law는 평균 시스템 내 작업 수 L, 도착률 λ, 평균 체류 시간 W의 관계를 `L = λW`로 나타낸다. 시스템 경계를 어디에 두는지 일관되어야 한다. API 도착률과 GPU 커널 시간만 섞으면 대기·전처리를 빠뜨릴 수 있다.

예: 완료까지 평균 0.2초, 안정된 처리율 50건/초라면 평균 시스템 내 작업 수는 약 10건이다. 하지만 동시성 제한을 10으로 정하면 충분하다는 의미는 아니다. 피크와 지연 분포가 있기 때문이다.

**연습:** 120건/초, 평균 체류 0.4초이면? `48건`. 평균 체류 시간이 0.8초로 늘면 같은 도착률에서 시스템 내 작업은 `96건` 수준이 된다.

## 2. 워커 수와 여유율

작업 한 건 평균 실행이 0.5초이고 워커는 순차 처리한다고 하자. 워커 한 개의 단순 처리율은 2건/초다. 도착률 12건/초에서 처리율만 맞추려면 6개지만 이용률이 100%에 가까우면 작은 변동에도 대기가 늘 수 있다.

목표 이용률 60%라는 학습 가정이라면 필요한 수는 `ceil(12 × 0.5 / 0.6) = 10개`다. 60%는 보편적 권장값이 아니라 이 예제에서 정한 여유율이다. 실제 값은 부하 시험으로 결정한다.

## 3. 장애 후 용량

각 AZ에 3대, 서버당 40건/초이면 총 240건/초다. 한 AZ를 잃으면 120건/초만 남는다. 피크가 180건/초라면 정상 시 충분해도 장애 중에는 부족하다.

요구가 '한 AZ 장애 중 피크 유지'라면 각 AZ의 남는 용량·다른 AZ의 확장 속도·요청 제한 전략을 함께 설계한다. 용량 확보 시간을 복구 시간 목표에 포함한다.

## 4. 큐 해소 시간

기존 적체 B=1,200건, 도착률 λ=8건/초, 처리율 μ=12건/초라면 순감소는 4건/초다. 일정한 비율이라는 가정 아래 해소 시간은 `B/(μ-λ)=300초`다.

μ=λ이면 적체가 줄지 않는다. μ<λ이면 더 쌓인다. `B/μ`만 계산하면 계속 들어오는 새 작업을 무시한 것이다.

**연습:** B=900, λ=15, μ=20 → 180초. μ=14라면 유한한 해소 시간을 계산할 수 없다.

## 5. 지연 백분위

평균은 모든 값의 합/개수다. p95는 대략 95%가 그 이하인 경계를 나타내며 계산 방식에 따라 작은 표본에서 값이 다를 수 있다. 실습에서는 nearest-rank 정의를 사용한다.

요청 100개 중 95개가 100ms, 5개가 3,000ms라면 평균은 245ms다. 이 데이터에서 nearest-rank p95는 100ms, p99는 3,000ms다. p95만 보면 가장 느린 5%를 놓칠 수 있다. 표본 수와 측정 기간을 같이 적는다.

서로 다른 서버의 p95를 평균내서 전체 p95라고 할 수 없다. 전체 분포를 합치거나 적절한 히스토그램 집계가 필요하다.

## 6. 모델 배칭의 절충

배치를 키우면 장치 처리 효율이 좋아질 수 있지만 모을 때까지 기다리는 시간이 늘어난다. 전체 지연은 대기+전처리+전송+추론+후처리로 본다. GPU 실행 시간만 줄여도 API 총지연은 나빠질 수 있다.

실험 표:

| 배치 크기 | 처리량 | p95 총지연 | 메모리 | 판단 |
|---|---|---|---|---|
| 1 | 직접 측정 | 직접 측정 | 직접 측정 | 실시간 기준 |
| 4 | 직접 측정 | 직접 측정 | 직접 측정 | 개선 여부 |
| 16 | 직접 측정 | 직접 측정 | 직접 측정 | 지연 요구 충족? |

수치를 만들어 채우지 않는다. 현재 4070 Ti SUPER에서 측정한 값은 다른 클라우드 GPU의 성능을 그대로 보장하지 않는다.

## 7. 손익분기 계산

가상 방식 A: 월 고정비 20 + 요청당 0.000002.
가상 방식 B: 월 고정비 2 + 요청당 0.000008.

같아지는 N은 `20 + .000002N = 2 + .000008N`, 따라서 `N=3,000,000`건이다. 그보다 작은 요청량이면 이 두 항목만으로는 B가 저렴하고, 크면 A가 저렴하다.

현실에서는 메모리·실행시간·전송·로그·항상 켜진 부하 분산기 등 항목이 추가된다. 계산 결과를 서비스 전체 요금 비교로 확대하지 않는다.

## 8. 민감도 분석

한 숫자만 제시하지 말고 요청량 0.5배/1배/2배, 저장 기간 7일/30일/90일, 캐시 적중률 50%/80%/95%를 바꾸어 보자. 어떤 가정이 비용에 가장 큰 영향을 주는지 찾는다.

예: 요청량 100만, 적중률 80%이면 원본 조회는 단순 계산으로 20만 회다. 적중률 50%면 50만 회로 늘어난다. 다만 캐시 유지 비용과 무효화 비용도 있다.

## 제출 과제

분류 API의 입력 크기·요청량·평균/p95 지연·모델 메모리·저장 기간을 표로 작성한다. 미측정 값은 '가정'으로 표시한다. 워커 수·AZ 장애 용량·큐 해소 시간·비용 민감도를 각각 계산한다.
