# 5장. 실패해도 중복 효과를 만들지 않는 작업 처리

[목차](README.md)

## 1. 정확히 어디서 실패했는가

작업 처리 흐름을 쪼개면 중복 문제가 드러난다.

```text
메시지 수신 → 입력 검증 → 실행 → 결과 저장 → 메시지 삭제
```

| 실패 시점 | 재전달 시 위험 | 설계 질문 |
|---|---|---|
| 실행 전 | 같은 작업 다시 시작 | 작업이 재실행 가능한가? |
| 실행 중 | 일부 결과만 남음 | 임시 결과와 완료 결과 구분? |
| 저장 후 삭제 전 | 결과 중복 기록 | 작업 ID로 중복 효과 제어? |
| 외부 통지 후 상태 기록 전 | 알림 중복 발송 | 외부 호출에도 멱등 키 지원? |

메시지 시스템이 중복을 줄여도 외부 효과까지 자동 해결하지는 않는다.

## 2. 작업 상태 모델

```text
PENDING → RUNNING → SUCCEEDED
                 → RETRYABLE_FAILURE
                 → PERMANENT_FAILURE
```

RUNNING 상태에는 시작 시각·시도 번호·소유 워커·임대 만료 같은 정보를 둘 수 있다. 워커가 죽으면 누가 작업을 다시 맡을지 결정해야 한다. 임대만 만료되었다고 이전 워커가 반드시 멈춘 것은 아니므로 결과 기록 조건에 주의한다.

완료 상태를 조건부로 기록하는 접근과 외부 부수 효과까지 묶는 접근은 다르다. DB에 '완료'만 한 번 기록되어도 이메일은 두 번 발송될 수 있다.

## 3. 멱등 키의 범위

`request_id`가 같다면 입력도 같아야 한다는 계약을 정할 수 있다. 동일 ID에 다른 입력이 오면 기존 결과를 무조건 반환하기보다 충돌로 처리한다. 입력 해시에는 모델 버전·전처리 버전 등 결과를 바꾸는 조건을 포함할지 결정한다.

입력 JSON의 키 순서처럼 의미가 같은 표현 차이는 정규화해 해시를 계산할 수 있다. 부동소수점 표현·타임존·기본값은 정규화 규칙이 필요하다.

## 4. Visibility timeout

수신 후 메시지가 다시 보이기까지의 기간을 작업 시간과 맞춘다. 너무 짧으면 아직 처리 중인데 다시 전달될 수 있고, 너무 길면 실패한 작업의 재시작이 늦어진다. 긴 작업은 적절한 연장을 검토한다.

그러나 timeout을 길게 정해도 SQS의 전달 특성상 중복이 완전히 불가능해지는 것은 아니다. 소비자는 중복을 견딜 수 있어야 한다.

예: 평소 20초, 드물게 90초 작업이라면 평균 20초만 보고 제한을 정하면 꼬리 지연 작업에서 중복 가능성이 커진다. 처리 시간 분포와 실패 복구 목표를 함께 본다.

## 5. 재시도 폭풍

한 요청을 네트워크 클라이언트가 최대 3회, API가 최대 3회, 워커가 최대 3회 시도하면 최악의 단순 조합에서 하위 호출이 27회까지 늘 수 있다. 각 계층이 독립적으로 재시도하면 장애를 증폭할 수 있다.

지수 backoff 예: 1, 2, 4, 8초. 상한을 두고 jitter로 시점을 흩어 동시 재시도를 완화한다. 영구적인 입력 오류를 같은 값으로 재시도하는 것은 보통 의미가 없다.

시간 초과는 실패 확정이 아닐 수 있다. 상대 서버가 처리를 완료하고 응답만 잃었을 가능성을 고려한다.

## 6. Lambda와 SQS 배치 실패

배치 10건 중 1건만 실패했는데 전체 배치를 실패로 처리하면 성공한 9건도 재전달될 수 있다. 지원되는 partial batch response를 설정하고 실패 항목을 올바르게 보고하면 불필요한 재처리를 줄일 수 있다.

설정과 코드 응답 형식이 함께 맞아야 한다. FIFO의 순서 요구에서는 첫 실패 이후 미처리 항목을 다루는 방식도 공식 지침을 확인한다. 부분 응답을 켠다고 소비자의 멱등성이 불필요해지는 것은 아니다.

## 7. 큐가 있다고 무한 부하를 받을 수 있는 것은 아니다

도착률이 초당 100건, 처리율이 초당 80건이면 매초 약 20건이 쌓인다. 10분 동안 계속되면 단순 계산으로 12,000건이 늘어난다. 입력 제한, 워커 확장, 작업 우선순위, 최대 대기 시간 등 정책이 필요하다.

큐 길이만 보지 말고 가장 오래 기다린 메시지의 나이도 본다. 작업 하나가 오래 걸리는 시스템에서는 작업 수와 남은 작업량이 다를 수 있다.

## 8. 설계 과제

영상 분석 결과를 DB에 저장하고 완료 알림을 보내야 한다. 워커는 언제든 종료될 수 있다.

풀이에 포함할 것: 작업 ID, 입력 충돌, RUNNING 만료, 결과 저장 조건, 알림 상태, 재시도 상한, DLQ 조사, 재처리 절차. DB 변경과 알림 이벤트를 같은 트랜잭션에 기록하는 outbox 패턴도 검토할 수 있지만 실제 발송 소비자는 여전히 중복을 고려해야 한다.

참고: [SQS visibility](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), [Lambda와 SQS](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html), [부분 배치 응답](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html).
