# 1장. 권한을 '붙이는 것'에서 '증명하는 것'으로

[목차](README.md)

## 목표

AccessDenied를 보고 관리자 권한부터 붙이지 않고, **누가 어떤 자원에 어떤 작업을 요청했는지** 먼저 적는다. 이 장의 핵심은 정책을 한 장만 보는 습관에서 벗어나는 것이다.

## 1. 두 개의 호출을 구분한다

계정 A의 개발자가 계정 B의 역할을 맡아 B의 S3 모델을 읽는다.

```text
A의 개발자 → STS AssumeRole → B 역할의 임시 세션 → S3 GetObject
```

여기에는 적어도 두 권한 질문이 있다.

1. A의 개발자가 B 역할을 맡을 수 있는가?
2. B 역할 세션이 S3 객체를 읽을 수 있는가?

역할을 맡을 수 있다는 사실만으로 모든 B 자원이 열리는 것은 아니다. 첫 요청의 trust policy와 두 번째 요청의 permissions policy는 목적이 다르다.

### 가상 사례

- 개발자 계정: `111111111111`.
- 모델 보관 계정: `222222222222`.
- 대상 역할: `ModelReader`.
- 버킷: `example-study-private-models`.

첫 단계에서는 호출자의 역할 전환 허용과 대상 역할의 신뢰 관계 등 적용 조건을 확인한다. 두 번째 단계에서는 전환 후 주체의 읽기 권한과 대상 자원의 정책을 확인한다. STS 전환 이후에도 계속 A의 원래 권한으로 S3를 호출한다고 생각하면 진단이 틀어진다.

## 2. 정책의 역할을 구분한다

| 정책 | 질문 | 그 자체로 하지 않는 일 |
|---|---|---|
| Identity policy | 이 주체에게 어떤 작업을 허용할까? | 네트워크 경로 생성 |
| Resource policy | 이 자원을 누가 사용할 수 있을까? | 모든 호출자의 다른 자원 접근 허용 |
| Trust policy | 누가 이 역할을 맡을 수 있을까? | 역할의 모든 서비스 권한 정의 |
| Permissions boundary | 이 IAM 주체의 권한 범위를 어디까지로 제한할까? | 단독 권한 부여 |
| Session policy | 이 임시 세션을 어떤 범위로 제한할까? | 원래 역할 범위를 넘는 권한 부여 |
| SCP | 조직의 해당 계정에 어떤 권한 제한을 적용할까? | IAM 권한 직접 부여 |

**주의:** 같은 계정의 resource policy는 사용자 ARN, 역할 ARN, 역할 세션 ARN 등 어떤 주체를 지정하느냐에 따라 implicit deny와의 관계가 달라질 수 있다. '모든 정책을 언제나 단순 교집합하면 된다'는 규칙은 완전한 IAM 평가기가 아니다. 명시적 거부와 세부 예외를 공식 평가 문서에서 확인한다.

## 3. 정책 읽기 실습

다음은 지정한 경로의 객체 읽기를 허용하는 역할 권한 예제다. 실행하거나 계정에 등록하는 자료가 아니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-study-private-models/releases/*"
  }]
}
```

직접 판정:

| 요청 | 이 정책의 허용과 일치? | 이유 |
|---|---|---|
| releases/v1.bin GetObject | 예 | 작업과 객체 경로 일치 |
| datasets/train.csv GetObject | 아니오 | 경로 불일치 |
| releases/v1.bin DeleteObject | 아니오 | 작업 불일치 |
| 버킷 ListBucket | 아니오 | 작업과 ARN 유형이 다름 |

표의 '예'는 이 정책에 허용 문장이 있다는 뜻이다. 최종 접근 성공을 보장하지 않는다. 적용되는 다른 거부·조건·키 권한 등을 더 살펴야 한다.

## 4. S3 읽기와 KMS 복호화는 별도 관문

모델이 고객 관리형 KMS 키로 암호화되어 있다면 객체 접근뿐 아니라 필요한 키 사용 권한도 살핀다. S3에서 허용됐는데 복호화가 거부될 수 있다. 반대로 키 사용 권한만 있어도 객체 읽기 권한이 자동으로 생기지는 않는다.

진단 기록 예:

```text
주체: ModelReader 역할 세션
작업: s3:GetObject
자원: releases/v1.bin
객체 정책: 허용 경로 확인
키: 어떤 KMS 키인지 확인
키 정책/주체 권한: 필요한 복호화 접근 확인
오류 위치: 객체 접근 단계인지 키 사용 단계인지 로그 확인
```

오류 메시지는 서비스와 호출 방식에 따라 정보가 제한될 수 있으므로 예상만으로 단정하지 않는다. 감사 기록과 실제 설정을 연결한다.

## 5. 조건을 넣는 이유

같은 작업이라도 특정 조직·태그·네트워크 경로·전송 방식에서만 허용하고 싶을 수 있다. 조건 키는 서비스와 호출 맥락에 따라 존재 여부가 다르다. 필요한 키가 항상 포함된다고 가정하면 정상 서비스 호출을 차단할 수 있다.

예를 들어 특정 VPC endpoint를 통해서만 접근하게 했다면, 개발자 PC에서 직접 호출하는 요청은 같은 역할이어도 조건을 만족하지 못할 수 있다. 콘솔에서 성공하는지와 실제 워크로드가 성공하는지를 각각 확인해야 한다.

## 6. 최소 권한을 만드는 절차

1. 기능별 API 작업을 적는다: 모델 읽기, 결과 쓰기, 로그 기록.
2. 각 작업의 대상 자원을 적는다.
3. 기능에 불필요한 삭제·계정 관리·정책 변경 권한을 제외한다.
4. 정상 요청뿐 아니라 허용하면 안 되는 요청도 검사한다.
5. 장애 조사에 필요한 관찰 권한과 실행 권한을 분리한다.

작업을 제한했어도 `Resource: *`가 필요한 서비스 작업이 존재한다. 모든 와일드카드를 기계적으로 오류라고 판단하지 말고 그 API의 자원 수준 권한 지원 여부를 확인한다.

## 7. 확인 문제와 풀이

**문제:** 역할 전환은 성공했고 S3 ListBucket도 성공했다. 하지만 GetObject가 실패한다. 가능한 원인 세 가지를 적어라.

**풀이:** 목록과 객체 읽기는 별도 작업이므로 GetObject 허용이 없을 수 있다. 허용한 객체 접두사와 실제 키가 다를 수 있다. 대상 정책의 명시적 거부 또는 KMS 키 접근 문제일 수 있다. 전송·엔드포인트 조건도 후보다. 목록 성공은 객체 읽기 전체 성공의 증거가 아니다.

**추가 과제:** 버킷 읽기 오류와 API 사용자 인증 오류를 구분하는 체크리스트를 만든다. API 사용자는 인증됐지만 서버 역할이 모델을 읽지 못할 수도 있다.
