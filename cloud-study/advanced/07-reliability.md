# 7장. 목표를 정하고 복구를 검증하기

[목차](README.md)

## 1. SLI·SLO·SLA

SLI는 측정 지표, SLO는 내부적으로 달성하려는 목표, SLA는 계약상의 약속과 조건을 의미한다. 여기서는 학습용 SLO를 정의한다. 클라우드 제공자의 SLA를 내 애플리케이션의 SLA와 같은 것으로 취급하지 않는다.

예: '한 달 동안 유효한 예측 요청의 99.9%가 성공한다.' 이 문장에는 분모·분자·기간을 정의해야 한다. 잘못된 사용자 입력은 성공률 계산에서 어떻게 다룰지, 429는 어떤 기준으로 포함할지 미리 정한다.

## 2. 오류 예산

요청 기반 목표가 99.9%, 대상 요청이 1,000,000건이면 실패 허용량은 1,000건이다. 이미 400건 실패했다면 단순 잔여 예산은 600건이다.

시간 기반 목표를 따로 정의해 30일×24시간×60분×0.001을 계산하면 43.2분이다. 요청 기반의 1,000건과 시간 기반의 43.2분은 같은 지표가 아니다. 트래픽이 많은 시간의 장애는 요청 기반 영향이 더 클 수 있다.

## 3. 여러 의존 서비스

A와 B가 모두 작동해야 성공하는 단순 구조에서, 독립이라는 강한 가정 아래 가용성은 곱으로 계산할 수 있다. 각각 99.9%라면 약 99.8001%다.

현실에서는 동일 Region·계정·배포·네트워크를 공유해 장애가 상관될 수 있다. 그러므로 곱 계산은 직관용이며 계약상의 보장이 아니다. 공유 장애 원인을 찾는 것이 숫자만 곱하는 것보다 중요하다.

## 4. Canary 배포

일부 트래픽에 새 버전을 보내고 지표를 비교한다. 모델 API에서는 오류율·지연뿐 아니라 입력 스키마·예측 분포·유효한 품질 지표도 살핀다. 실제 정답이 늦게 도착하면 즉시 정확도를 알 수 없으므로 관찰 가능한 지표와 사후 평가를 구분한다.

단계 예: 내부 테스트 → 1% → 10% → 50% → 전체. 이는 예제 비율이며 실제 표본 수와 위험에 맞춰 정한다. 1%가 너무 적어 드문 오류를 발견하지 못할 수도 있다.

중단 기준을 먼저 쓴다: 오류율 증가, 특정 입력군 실패, p95 목표 초과, 결과 스키마 위반. 결과를 보고 유리하게 기준을 바꾸지 않는다.

## 5. DB 스키마와 롤백

애플리케이션을 이전 버전으로 되돌려도 DB 스키마가 비호환으로 바뀌면 복구되지 않는다. 새 필드를 추가하고 양쪽 버전이 읽을 수 있게 한 뒤 나중에 이전 필드를 제거하는 확장-축소 방식 등을 고려한다.

순서 예:

1. 이전 코드와 호환되는 필드 추가.
2. 새 코드가 양쪽 형식을 이해하도록 배포.
3. 데이터 이행·검증.
4. 이전 버전 사용이 끝난 뒤 오래된 구조 제거.

이 과정에서도 쓰기 정합성과 부분 이행 상태를 점검해야 한다.

## 6. 복구 시간은 복원 명령 시간만이 아니다

```text
복구까지 걸린 시간 = 감지 + 판단 + 자원 준비 + 데이터 복원 + 연결 전환 + 검증
```

예: 감지 5분, 판단 10분, 자원 준비 15분, 복원 20분, 전환 5분, 검증 10분이면 총 65분이다. DB 복원 20분만 기록하면 실제 RTO를 과소평가한다.

대기 환경의 할당량, 비밀정보, 이미지, DNS, 인증서도 준비돼야 한다. 서버 이미지가 있어도 필요한 모델·키가 없으면 복구할 수 없다.

## 7. 장애 훈련 보고서

- 시나리오: 어떤 구성 요소가 어떤 방식으로 실패했는가?
- 기대 행동: 어디로 전환하고 어느 요청이 실패할 수 있는가?
- 실제 관찰: 타임스탬프·오류 수·전환 시간.
- 데이터 검증: 누락·중복·손상 여부.
- 복구 판정: 단순 헬스 체크와 실제 기능을 모두 확인했는가?
- 개선: 담당자·기한·재검증 방법.

여기서는 실제 운영 자원에 장애를 일으키지 않는다. 로컬 실험과 테이블탑 연습으로 시작한다.

## 과제

목표 RTO 30분인데 현재 감지부터 검증까지 65분이다. 무엇을 줄일 수 있을까? 자동 감지, 사전 배포된 환경, 복원 절차 자동화, 검증 스크립트 등이 후보지만 비용과 오작동 위험을 함께 적는다.
