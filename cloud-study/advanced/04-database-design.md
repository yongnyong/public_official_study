# 4장. 일관성·캐시·전환을 함께 설계하기

[목차](README.md)

## 1. 최신 값이 필요한 곳을 구분한다

예측 작업을 접수하고 바로 상태 화면을 열었는데 '없음'이라고 나온다. 실제 작업이 사라진 것일까? 원본에 쓰고 비동기 복제본이나 인덱스에서 읽었다면 반영 지연일 수 있다.

처음부터 모든 읽기를 동일하게 취급하지 않는다.

| 읽기 | 허용 지연 | 설계 방향 |
|---|---|---|
| 방금 접수한 작업 확인 | 최신 상태 중요 | 지원되는 강한 읽기 경로 또는 원본 확인 |
| 주간 집계 | 일정 지연 허용 | 분석 저장·복제본 등 검토 |
| 공개 통계 대시보드 | 요구에 따른 지연 허용 | 캐시·집계 갱신 |
| 권한 변경 직후 접근 | 오래된 권한 위험 | 일관성·캐시 무효화 정책 명확화 |

## 2. DynamoDB 테이블과 GSI

테이블에서 가능한 읽기 일관성 선택을 GSI에도 그대로 적용할 수 있다고 생각하면 안 된다. GSI 읽기는 최종적 일관성이다. 기본 테이블 반영과 인덱스 반영을 같은 순간으로 가정하지 않는다.

예: 작업 ID로 기본 키 조회가 가능한데, 굳이 '사용자별 작업 목록' GSI에서 새 작업 존재 여부를 판정하면 반영 지연 때문에 혼란이 생길 수 있다. 쓰기 직후의 확인 경로와 검색 목록 경로를 분리한다.

Global Tables는 현재 제공되는 일관성 모드와 Region 지원 조건을 확인해야 한다. '다중 Region은 언제나 동일 방식의 최종 일관성'으로 단정하지 않는다. 시험·설계의 구체적인 모드와 요구를 읽는다.

## 3. Aurora reader endpoint의 의미

reader endpoint의 분산은 연결 단위 관점으로 이해한다. 오래 유지되는 연결 하나에서 실행하는 모든 SQL이 매번 다른 reader에 분산된다고 가정하지 않는다. 연결 풀의 수명과 분산 상태가 실제 부하에 영향을 줄 수 있다.

장애 전환 후 애플리케이션이 예전 연결을 계속 붙잡고 있으면 endpoint가 있다는 사실만으로 즉시 정상화되지 않는다. 재연결, DNS 캐시, 타임아웃, 실패한 트랜잭션 재시도를 점검한다.

재시도할 때 이전 쓰기가 성공했는지 모를 수도 있다. 네트워크 응답이 없다는 것과 서버에서 실행되지 않았다는 것은 다르다.

## 4. Cache-aside의 경쟁 상황

다음 순서를 손으로 따라가자.

1. A가 캐시 미스를 보고 DB의 값 v1을 읽는다.
2. B가 DB를 v2로 바꾸고 캐시를 삭제한다.
3. A가 조금 늦게 캐시에 v1을 저장한다.
4. 이후 읽기는 TTL 동안 v1을 받을 수 있다.

'쓰고 캐시 삭제'라는 한 문장만으로 모든 경쟁이 해결되지는 않는다. 버전 검증, 짧은 TTL, 이벤트 기반 무효화, 요구에 맞는 다른 쓰기 전략을 검토한다. 모든 방식은 복잡도·지연·정확성의 절충이 있다.

## 5. Cache stampede

인기 키가 동시에 만료되면 많은 요청이 원본으로 몰린다. 대책 후보는 TTL에 작은 변동 추가, 같은 키의 동시 로딩 합치기, 사전 갱신, 허용되는 경우 오래된 값 임시 제공 등이다.

개인별 비밀정보나 즉시 반영해야 하는 권한 정보는 오래된 값 제공이 적절하지 않을 수 있다. 캐시 최적화는 데이터 의미를 무시하고 적용할 수 없다.

## 6. 마이그레이션 절차

원본 DB를 다른 환경으로 옮길 때 다음 단계를 구분한다.

1. **발견:** 테이블·인덱스·트리거·외부 의존·문자 인코딩 확인.
2. **스키마:** 대상 엔진에서 호환되는지 검증.
3. **초기 적재:** 기준 시점 데이터 복사.
4. **변경 반영:** 이전 중 새로 발생한 변경 추적.
5. **검증:** 행 수뿐 아니라 핵심 합계·샘플·질의 결과 비교.
6. **전환:** 쓰기 중단 범위·마지막 반영·endpoint 변경.
7. **관찰:** 오류·지연·누락 확인.
8. **되돌리기:** 새 환경에 발생한 쓰기를 어떻게 처리할지 포함.

DMS를 쓴다는 사실만으로 서로 다른 엔진의 모든 스키마·기능이 자동 변환된다고 생각하면 안 된다. 도구의 지원 범위와 애플리케이션 차이를 검증한다.

## 7. 확인 과제

**요구:** 사용자는 작업 접수 직후 자신의 작업을 볼 수 있어야 하고, 전체 작업 통계는 5분 지연을 허용한다.

**권장 풀이 방향:** 접수 직후 확인은 작업 ID 중심으로 최신 상태를 얻는 지원 경로를 사용한다. 통계는 비동기 집계·캐시를 사용할 수 있다. 한 읽기 경로에 상반된 요구를 모두 강요하지 않는다. 반환 응답에 접수된 ID와 상태를 포함하면 사용자 경험도 명확해진다.
