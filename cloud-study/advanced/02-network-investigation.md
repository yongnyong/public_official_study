# 2장. 왕복 경로를 추적하는 네트워크 진단

[목차](README.md)

## 1. 패킷이 지나가는 표를 만든다

API가 DB에 연결하지 못한다면 보안 그룹을 모두 여는 대신 다음 표를 작성한다.

| 단계 | 확인할 정보 | 관찰 근거 |
|---|---|---|
| 이름 해석 | DB 호스트가 어떤 주소로 해석되는가? | DNS 조회 |
| 출발 | API의 ENI·서브넷·주소는? | 자원 구성 |
| 경로 | 목적지에 맞는 라우트는? | 실제 연결된 라우팅 테이블 |
| 통과 규칙 | SG·NACL·OS 규칙은? | 규칙과 연결 추적 |
| 도착 | DB 리스너·포트·상태는? | DB 상태·로그 |
| 반환 | 응답이 돌아갈 경로와 규칙은? | 역방향 검토 |

다른 서브넷의 라우팅 테이블을 보고 정상이라고 판단하는 실수가 흔하다. 실제 association을 확인한다.

## 2. Longest prefix match 손풀이

학습용 경로표:

```text
10.0.0.0/16   → local
10.20.0.0/16  → peering-A
10.20.5.0/24  → inspection-path
0.0.0.0/0     → default-egress
```

- `10.20.5.12`: /16과 /24와 /0에 맞지만 가장 구체적인 /24 선택.
- `10.20.8.12`: /16 선택.
- `8.8.8.8`: /0 선택.

이것은 목적지 접두사 선택 원리를 위한 표이며 배포 템플릿이 아니다. 실제 AWS에서 local 경로·정적/전파 경로·동일 접두사 우선순위 및 지원 대상에는 추가 규칙이 있다.

**시험 함정:** 기본 경로가 정상이어도 더 구체적인 잘못된 경로가 있으면 일부 주소만 실패할 수 있다.

## 3. 보안 그룹 참조의 의미

API 보안 그룹이 DB의 허용 소스로 지정되면 'API 역할을 가진 모든 프로그램'이라는 뜻이 아니다. 네트워크 인터페이스에 연결된 보안 그룹과 지원되는 트래픽 경로의 의미다. IAM 역할과 SG ID는 다른 계층이다.

프록시·중간 장비·다른 네트워크를 거치는 경우 원본 주소와 SG 참조 지원 조건이 달라질 수 있다. 아키텍처 그림의 화살표를 실제 연결로 해석해야 한다.

## 4. NACL과 임시 포트

클라이언트가 DB 5432 포트에 접속한다고 하자. 목적지 포트는 5432지만 클라이언트의 출발 포트는 임시 포트다. 응답은 그 임시 포트로 돌아온다. 상태를 추적하지 않는 NACL에서는 반환 경로도 허용되어야 한다.

실제 임시 포트 범위는 운영체제와 자원 유형에 따라 다르므로 하나의 범위를 모든 환경의 정답처럼 외우지 않는다. 경로별 프로토콜·출발/목적 포트를 표로 적는 것이 안전하다.

```text
요청: API_IP:임시포트 → DB_IP:5432
응답: DB_IP:5432 → API_IP:임시포트
```

## 5. NAT·엔드포인트를 고를 때

요구가 '비공개 서버에서 S3로 접근'이면 관련 엔드포인트를 비교할 수 있다. 요구가 '임의의 외부 웹 API 접근'이면 S3 endpoint만으로 해결되지 않는다. 네트워크 경로, DNS, endpoint policy, 대상 서비스 권한을 따로 확인한다.

Interface endpoint 사용에서 private DNS 설정이 기대대로 동작하는지 점검한다. 이름은 정상 해석되지만 의도한 사설 경로가 아닐 수도 있다. Endpoint를 만들었다는 사실만으로 모든 워크로드가 그것을 사용한다는 보장은 없다.

비용 비교에는 시간당 자원 비용뿐 아니라 처리량·교차 AZ·전송 경로를 포함한다. 구체적 요금은 Region과 유형에 따라 현재 계산기에서 확인한다.

## 6. 진단 도구의 역할

- Flow Logs: 허용/거부 등 네트워크 흐름을 조사하는 자료. 애플리케이션 JSON 본문을 읽는 도구가 아니다.
- Reachability Analyzer: 지원 자원의 구성 기반 경로 분석. 실제 서비스가 올바른 비즈니스 응답을 한다는 증거는 아니다.
- 애플리케이션 로그: 인증 실패·입력 오류·DB 예외를 확인한다.
- DNS 조회: 해석되는 주소를 확인한다. TCP 연결 성공까지 보장하지 않는다.

## 7. 사례: 같은 서버에서 S3는 되고 외부 API만 안 된다

가능한 가설: S3는 endpoint 경로로 정상 접근하고 외부 인터넷 egress 경로는 없거나 잘못되어 있다. 또는 외부 대상의 DNS·포트·보안 조건 문제가 있다.

다음 행동: S3 성공만으로 인터넷 전체 연결이 있다고 판단하지 않는다. 두 목적지의 DNS 결과와 선택 경로를 비교한다. 과도하게 넓은 권한 부여로 네트워크 문제를 덮지 않는다.

## 8. 사례: ALB는 정상인데 일부 요청만 실패

확인 순서: 실패가 특정 target에 집중되는지 → AZ·버전별 차이 → 상태 확인은 실제 준비 상태를 반영하는지 → 세션·모델 캐시가 서버별로 다른지 → DB 연결 문제가 특정 자원에만 있는지.

원인은 네트워크일 수도, 배포 상태일 수도 있다. 패킷 경로와 요청 로그를 연결해 가설을 좁힌다.

## 제출 과제

두 AZ의 ALB→API→DB 경로를 그리고 정상/장애 경로를 다른 색으로 표시한다. 각 연결에 출발·목적 포트, 관련 SG, 라우팅 테이블을 적는다. DB 인증 실패가 발생하면 어떤 네트워크 검사가 이미 통과했을 가능성이 있는지도 설명한다.
