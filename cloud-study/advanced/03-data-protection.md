# 3장. 모델 데이터의 접근·보존·복구

[목차](README.md)

## 1. 세 가지 질문은 다른 질문이다

**누가 읽는가**, **얼마나 보관하는가**, **망가졌을 때 무엇으로 복원하는가**를 각각 적는다. 암호화된 자료도 권한 있는 사용자가 삭제할 수 있고, 복제된 자료에도 논리적 오류가 반영될 수 있다. 한 기능 이름으로 세 문제를 모두 해결했다고 판단하지 않는다.

예를 들어 모델 원본·학습 중간 산출물·사용자 입력·예측 로그는 보관 요구가 다르다. 원본 모델은 배포 재현을 위해 보관하지만 임시 파일은 짧게 유지할 수 있다. 실제 대회 자료라면 제공 약관과 반출 조건을 먼저 따른다.

## 2. 버전 관리로 삭제를 이해하기

버전 관리가 활성화된 일반 S3 버킷에서 단순 삭제는 삭제 마커를 추가하는 방식으로 동작할 수 있다. 이전 버전의 영구 삭제와 현재 키를 보이지 않게 하는 것은 다르다. 버전 ID를 명시한 삭제는 다른 결과를 만들 수 있다.

학습 시나리오:

```text
t0: model.bin → 버전 A
t1: model.bin → 버전 B 업로드
t2: 일반 삭제 → 현재 키에 삭제 마커
t3: 이전 버전을 지정해 복구 경로 검토
```

이때 저장 비용은 현재 버전만이 아니라 남은 이전 버전도 영향을 줄 수 있다. 수명 주기를 설계할 때 현재 객체·이전 버전·삭제 마커·미완료 업로드 등 어떤 대상을 정리하는지 확인한다.

## 3. 불변 모델 릴리스

`latest.bin` 한 파일만 계속 덮어쓰면 장애 시 어떤 파일이 실행됐는지 알기 어렵다. 다음처럼 릴리스별 경로와 manifest를 사용하면 재현에 도움이 된다.

```text
releases/2026-09-16-a/model.bin
releases/2026-09-16-a/manifest.json
deployment/current-release.json
```

manifest 예시:

```json
{
  "release": "2026-09-16-a",
  "model_sha256": "실제 파일에서 계산할 값",
  "feature_schema": "v2",
  "preprocess_commit": "실제 커밋 ID",
  "runtime_image": "고정된 이미지 식별자"
}
```

포인터 변경과 서버 캐시 갱신은 별도다. 포인터가 B로 바뀌었어도 기존 서버는 A를 메모리에 보유할 수 있다. 응답 로그에 실제 로드한 버전을 남기면 전환 진행 상태를 확인할 수 있다.

## 4. Presigned URL을 이해하기

서버가 비공개 객체의 제한된 접근 URL을 발급하면 사용자가 직접 파일을 주고받도록 구성할 수 있다. URL 자체가 접근 능력을 가진 값이므로 불필요한 공유나 로그 노출을 피한다.

유효 시간은 URL에 적은 만료 시간만 보지 않는다. 임시 자격 증명으로 만들었다면 그 자격 증명이 먼저 만료되어 접근이 끝날 수 있다. 발급 주체의 권한과 정책 변경 등도 영향을 줄 수 있다.

예제: URL 만료를 60분 후로 정했지만 사용한 세션은 15분 후 종료된다. 이를 무조건 60분 동안 유효하다고 안내하면 안 된다. URL을 재발급하는 흐름과 업로드 완료 확인을 설계한다.

파일이 업로드됐다는 이벤트만으로 안전하고 유효한 입력이라고 단정하지 않는다. 크기·형식·실제 콘텐츠·대상 작업의 연결을 확인한다.

## 5. Object Lock·복제·백업 비교

| 요구 | 검토할 기능 | 남는 설계 질문 |
|---|---|---|
| 실수로 덮어쓴 모델 복구 | 버전 관리 | 이전 버전 보존 기간 |
| 정해진 기간 변경/삭제 제한 | Object Lock | 보존 모드·권한·요건 |
| 다른 위치에 사본 유지 | 복제 | 지연·실패·삭제 전파 설정 |
| 운영과 분리된 복구 | 백업·별도 계정 등 | 접근 경계·복구 테스트 |

Object Lock은 운영상 삭제 제한을 만들 수 있으므로 동작을 모른 채 실제 자료에 설정하지 않는다. 이 장은 설계 공부이며 보존 설정 실행을 요구하지 않는다.

## 6. 복구 보고서 연습

사건: 새 모델 B가 잘못된 특징 순서로 배포돼 예측이 틀렸다.

1. 영향 기간과 실제 실행 버전별 요청 수를 확인한다.
2. 검증된 모델 A와 호환 전처리·이미지를 식별한다.
3. 배포 포인터만 바꿀지 실행 환경도 바꿀지 결정한다.
4. 소규모 확인 요청으로 정확한 특징 순서를 검증한다.
5. 캐시가 이전의 잘못된 답을 계속 반환하는지 확인한다.
6. 복구 완료와 재처리해야 할 결과를 구분한다.

복구는 단순 파일 교체보다 넓은 작업이다. 잘못 저장된 예측 결과를 어떻게 표시·재계산할지도 필요하다.
