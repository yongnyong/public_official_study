# 핵심 개념 교재

이 문서는 학습용 핵심 설명이다. 시험 전체 범위를 대체하지 않으며, 8주차에 공식 가이드와 대조한다. [공식 문서 목록](07-sources.md)에서 세부 동작을 확인한다.

## 1. IAM: 누가 무엇을 할 수 있는가

인증은 요청 주체를 확인하는 것이고 인가는 허용된 작업인지 판단하는 것이다. 정책은 작업(Action), 대상(Resource), 조건(Condition)을 기술한다. 역할은 서비스나 사용자가 맡아 임시 자격 증명으로 작업하도록 구성할 수 있다.

예시: 모델 API 서버는 지정한 모델 파일 읽기만 필요하다. 전체 버킷 삭제 권한은 필요 없다. 권한 오류를 만났다고 관리자 권한을 붙이는 대신 요청 주체·작업·대상·거부 정책을 확인한다.

연습: 읽기 API에 필요한 권한과 업로드 담당자에게 필요한 권한을 구분하라. 정책 평가에서는 명시적 거부가 허용보다 우선한다는 기본 규칙을 기억하되 여러 정책 유형의 결합도 공식 문서에서 확인한다.

## 2. 네트워크: 주소, 경로, 허용 규칙

VPC는 논리적으로 분리된 네트워크다. 서브넷은 VPC 주소 범위의 일부이며 AZ에 속한다. 라우팅 테이블은 목적지별 경로를 결정한다. 보안 그룹은 연결을 허용하는 규칙이다. 경로가 있어도 보안 설정이 막으면 통신하지 못한다.

IPv4 공개 인터넷에 직접 연결하는 EC2를 예로 들면 적절한 공개 주소, 인터넷 게이트웨이 경로, 보안 규칙 등 조건이 함께 필요하다. 공개 서브넷에 배치했다고 무조건 외부 접근이 되는 것은 아니다.

보안 그룹은 상태 추적을 하며 NACL은 상태를 추적하지 않는다. NACL을 구성할 때 반환 트래픽까지 생각한다. NAT는 비공개 영역에서 외부로 나가는 연결에 사용될 수 있지만 인바운드 공개 서버를 대신하는 기능은 아니다.

연습: 요청 실패 시 DNS → 경로 → 보안 규칙 → 실행 프로세스·포트 → 애플리케이션 순서로 확인할 항목을 써라.

## 3. 저장소: 무엇을 어떻게 읽는가

| 선택지 | 기본 형태 | 생각할 질문 |
|---|---|---|
| S3 | 객체 | 파일을 키로 저장·조회하는가? |
| EBS | 블록 | EC2에 붙는 디스크가 필요한가? |
| EFS | 공유 파일 시스템 | 여러 실행 환경의 파일 공유가 필요한가? |

모델 파일은 S3에 보관하고 실행 시 내려받아 메모리에 로드할 수 있다. 모델을 요청마다 다시 다운로드하면 지연과 요청 비용이 늘 수 있다. 모델 갱신 시점과 캐시 정책을 정한다.

버전 관리는 덮어쓰기·삭제 실수 대응에 도움이 되지만 모든 재해복구 요구를 자동 충족하지 않는다. 보관 기간, 삭제 권한, 복제 필요성, 복구 테스트를 별도로 생각한다.

연습: 학습 원본, 임시 전처리 파일, 배포 모델 각각의 보관 기간과 삭제 가능 조건을 적어라.

## 4. DB: 접근 패턴부터 정하기

관계형 DB는 관계와 트랜잭션 요구를 먼저 살핀다. DynamoDB는 키 기반 접근 패턴과 데이터 분산 설계가 중요하다. 서비스 이름만 외워서 SQL이면 무조건 하나, NoSQL이면 무조건 하나로 선택하지 않는다.

전통적인 RDS Multi-AZ DB 인스턴스 구성의 대기 인스턴스는 읽기 확장용이 아니다. 읽기 복제본과 목적을 구분한다. RDS Multi-AZ DB 클러스터 등 다른 구성은 읽기 가능 여부가 달라질 수 있으므로 문제의 배포 유형을 확인한다.

연습: '장애 발생 시 빠른 전환'과 '읽기 요청 급증'이 각각 어떤 요구인지 설명하라.

## 5. 확장: 병목은 어디에 있는가

수직 확장은 한 서버를 크게, 수평 확장은 서버 수를 늘리는 방식이다. 로드 밸런서는 요청을 분산하고 상태 확인을 통해 비정상 대상을 제외하도록 구성한다. Auto Scaling은 설정한 조건에 따라 용량을 조정한다.

API 서버만 늘려도 DB 연결 수나 모델 로딩 시간이 병목이 될 수 있다. 평균 지연뿐 아니라 p95 지연, 오류율, 처리량을 함께 본다. 세션을 특정 서버 메모리에만 저장하면 서버 교체·확장이 어려워질 수 있다.

연습: 트래픽이 10배 증가했을 때 서버 외에 점검할 항목 3개를 적어라.

## 6. 비동기 처리와 중복

긴 작업은 요청을 큐에 넣고 워커가 처리하는 방식으로 분리할 수 있다. 사용자는 작업 ID로 상태를 확인한다. 재시도는 일시적 실패 대응에 도움이 되지만 같은 작업이 중복 실행될 수 있다.

멱등성은 동일 요청을 다시 처리해도 의도하지 않은 추가 결과를 만들지 않는 성질이다. 예측 결과 저장에는 작업 ID를 사용해 중복을 제어할 수 있다. DLQ는 반복 실패 메시지를 격리해 조사하는 데 도움이 된다.

연습: 동일 작업을 두 번 받았을 때 DB에 결과가 두 개 생기지 않도록 처리 흐름을 설계하라.

## 7. 관찰과 복구

메트릭은 수치 추이, 로그는 사건 기록, 추적 정보는 요청이 여러 구성 요소를 지나가는 흐름을 이해하는 데 쓰인다. CloudWatch는 운영 관찰, CloudTrail은 API 활동 감사, Config는 자원 구성 기록·평가 관점으로 구분해 공부한다.

RTO는 복구까지 허용하는 시간 목표, RPO는 허용 가능한 데이터 손실의 시간 범위 목표다. 매일 백업한다는 사실만으로 10분 RPO가 충족되지는 않는다. 장애 감지부터 실제 복구까지 연습해야 한다.

연습: '2시간 안에 복구, 최대 15분 데이터 손실 허용'을 RTO/RPO로 표현하고 필요한 백업·복제 전략을 설명하라.

## 8. 비용

컴퓨팅 시간뿐 아니라 저장 용량, 요청 수, 전송, 로그, 로드 밸런서, NAT 등의 비용을 살핀다. 서버를 중지해도 디스크 등 비용이 남을 수 있다. 무료 플랜·크레딧 조건은 가입 시기와 서비스에 따라 확인한다.

Spot은 중단을 견딜 수 있는 작업인지 먼저 판단한다. 약정형 할인은 사용량을 예측할 수 있을 때 검토한다. 개인 단기 실습을 위해 장기 약정을 먼저 구입할 이유는 없다.

연습: 한 시간만 실습한 뒤에도 남아 과금될 수 있는 리소스 3개를 적어라.
