# 4장. EC2·확장·컨테이너

[목차](README.md) · 다음: [저장소](05-storage.md)

## 1. 인스턴스 선택은 병목에서 시작

CPU가 바쁜가, 메모리가 부족한가, 디스크 I/O가 느린가, GPU가 필요한가? 병목에 맞게 자원을 선택한다. AI라고 모든 작업에 GPU가 필요한 것은 아니다. 작은 트리 모델 추론은 CPU로도 요구사항을 충족할 수 있고, GPU를 사용해도 입력 전처리가 병목이면 효과가 작을 수 있다.

AMI는 인스턴스를 시작할 이미지이고 launch template은 인스턴스 생성 설정을 재사용하게 한다. 프로그램 설치를 매번 수동으로 반복하는 대신 이미지·시작 설정·구성 관리로 재현성을 높인다.

## 2. 확장 계산 예시

서버 한 대가 목표 지연 내 초당 40건을 처리한다고 측정했다. 피크 100건/초에는 단순히 3대 분량이 필요하다. 3대 중 한 대가 고장 나면 80건/초 수준이므로 장애 중에도 목표를 유지하려면 추가 용량이나 다른 처리 전략이 필요하다.

이 계산은 예제다. 실제 성능은 요청 크기, 모델 버전, 캐시, 동시성에 따라 측정해야 한다. Auto Scaling은 순간적으로 무한한 용량을 제공하지 않으며 시작·모델 로딩 시간과 할당량을 고려한다.

## 3. ALB·NLB·상태 확인

ALB는 HTTP 계층의 경로·호스트 기반 라우팅 요구와 연결한다. NLB는 TCP/UDP 등 전송 계층 요구를 살핀다. 단순히 '더 빠른 것'을 고르는 문제가 아니다.

상태 확인이 `/health`를 호출한다고 하자. 프로세스는 살아 있지만 모델 로딩이 끝나지 않았다면 예측 준비가 안 된 상태다. 프로세스 생존 여부와 요청 처리 준비 상태를 구분하면 배포 중 오류를 줄이는 데 도움이 된다.

## 4. 상태를 외부로 분리하기

사용자 세션을 서버 한 대의 메모리에만 저장하면 요청이 다른 서버로 갈 때 문제가 생긴다. 필요한 상태를 공유 저장소로 분리하거나 토큰 방식 등을 검토한다. 다만 외부 저장소가 새로운 병목·장애 지점이 될 수 있어 함께 설계한다.

모델 캐시는 서버 메모리에 둘 수 있지만 원본 버전과 재로딩 절차를 정의한다. 서버 교체 시 같은 모델과 의존성을 복원할 수 있어야 한다.

## 5. EC2·ECS·EKS·Fargate

- EC2: 가상 서버의 제어권과 운영 책임을 갖는다.
- ECS: 컨테이너 워크로드를 배치하고 운영하는 서비스다.
- EKS: Kubernetes 기반 운영 요구와 연결한다.
- Fargate: 지원되는 컨테이너 워크로드에서 기반 서버 관리 부담을 줄이는 실행 방식이다.
- ECR: 컨테이너 이미지를 저장하는 레지스트리다.

레지스트리는 이미지를 보관하고 실행 환경은 컨테이너를 실행한다. 이 둘을 혼동하지 않는다. 특정 GPU·네트워크·실행 환경 요구는 선택한 방식이 지원하는지 먼저 확인한다.

## 6. 배포 실패에 대비하기

버전 A에서 B로 바꿀 때 입력·출력 스키마와 모델 전처리도 함께 바뀔 수 있다. 이미지 버전뿐 아니라 모델 버전·설정·의존성을 기록한다. 일부 트래픽부터 새 버전으로 보내는 점진 배포와 이전 버전 복구 절차를 설계할 수 있다.

완료 기준은 '컨테이너가 실행됐다'가 아니라 정상 요청, 잘못된 요청, 재시작, 버전 변경이 의도대로 처리되는 것이다.

## 확인 질문

1. CPU 30%인데 API가 느리면 무조건 CPU를 늘려야 하는가? → DB·외부 호출·I/O·락 등 다른 병목을 조사한다.
2. 로드 밸런서가 있으면 DB도 자동 이중화되는가? → 아니다. DB 계층을 별도 설계한다.
3. 이미지 저장소가 곧 실행 서버인가? → 아니다. ECR과 실행 환경의 역할을 구분한다.
