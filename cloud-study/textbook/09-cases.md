# 9장. 설계 사례 4개

[목차](README.md)

문제를 읽을 때 ①기능 ②성능 ③장애 ④보안 ⑤비용 ⑥운영 부담을 표시한다. 아래는 자체 제작 학습 사례이며 유일한 정답 아키텍처를 주장하지 않는다.

## 사례 1. 작은 분류 모델 API

요구: CPU로 실행 가능, 요청량 변동, 모델 파일 비공개, 배포 버전 추적.

접근: 먼저 로컬에서 모델 메모리·시작 시간·요청당 지연을 측정한다. 수치에 따라 함수·컨테이너·VM을 비교한다. API는 입력을 검사하고 모델 파일은 역할을 통해 읽는다. 배포 설정에는 모델 버전과 이미지 버전을 함께 기록한다.

설계 예시: 공개 API 진입점 → 비공개 실행 계층 → 비공개 모델 저장소. 관찰 정보에는 버전·처리시간·오류 유형을 기록한다.

잘못된 접근: 'AI니까 GPU 서버부터 켠다.' 이유: 작은 모델은 CPU로 충분할 수 있고 항상 켜진 GPU는 요구 대비 비쌀 수 있다.

검증: 정상·누락·잘못된 타입 입력, 모델 로딩 실패, 인스턴스 재시작, 이전 버전 복구. 성능과 모델 품질을 따로 기록한다.

## 사례 2. 긴 동영상 분석

요구: 작업당 오래 걸림, 사용자가 즉시 결과를 기다릴 필요 없음, 실패 시 다시 처리.

접근: 입력 저장 → 작업 ID 생성 → 큐 → 워커 처리 → 결과 저장 → 상태 조회. 워커는 작업 ID를 기준으로 중복 효과를 막고 실패 원인을 기록한다. 장기 작업에 맞는 가시성 제한·진행 상태 갱신을 설계한다.

잘못된 접근: HTTP 연결을 끝날 때까지 무조건 유지한다. 이유: 타임아웃·클라이언트 연결 종료가 작업 상태 관리와 얽힌다.

추가 질문: 동일 영상이 두 번 제출되면 같은 작업으로 볼 것인가? 모델 버전이 달라지면 결과를 재사용할 것인가? 파일 해시만 같다고 모든 실행 조건이 같은 것은 아니다.

## 사례 3. 읽기가 많은 게시판

요구: SQL 관계형 데이터, 읽기 급증, 쓰기 직후 일부 화면은 최신 값 필요.

접근: 인덱스와 질의를 먼저 확인한다. 읽기 복제본·캐시로 읽기 부하를 나눌 수 있지만 최신 값이 필요한 경로는 복제 지연과 캐시를 고려한다. 장애 대비는 DB 배포 구성과 복구 요구로 따로 설계한다.

잘못된 접근: 읽기 복제본만 만들면 쓰기 부하와 데이터 손실 문제가 모두 해결된다. 이유: 역할이 다르며 원본 쓰기와 백업·복구 설계가 남는다.

검증: 복제 지연, 캐시 만료, 쓰기 직후 조회, 원본 장애 전환 후 연결 복구.

## 사례 4. 월별 상권 분석

요구: 월별 파일 수집, 집계 결과 하루 이내 제공, 원본 재처리 가능.

접근: 원본을 변경하지 않는 영역에 보관하고 정제 자료를 별도 저장한다. 날짜·지역 등 질의 패턴을 보고 파티션을 설계한다. SQL 분석 또는 배치 ETL을 비교한다. 변환 코드 버전과 입력 기간을 기록한다.

잘못된 접근: 하루 이내 결과면 되는데 모든 것을 복잡한 실시간 스트림으로 만든다. 이유: 지연 요구보다 복잡도가 커질 수 있다.

검증: 중복 수집, 누락 파일, 스키마 변경, 재처리 결과 일치, 집계 총합 비교. 공모전 데이터를 쓸 때는 제공 약관에 맞는 저장·반출 범위를 먼저 확인한다.

## 제출 문서 틀

1. 요구사항과 가정.
2. 구조 그림과 데이터 흐름.
3. 선택한 서비스와 대안 제외 이유.
4. 권한·암호화·데이터 보관.
5. 장애 시 행동과 복구 목표.
6. 비용 항목과 사용량 가정.
7. 실제 검증한 결과와 아직 검증하지 않은 부분.

완료 기준: 다른 사람이 '왜 이 구조인가?'라고 물었을 때 요구사항으로 답할 수 있다.
