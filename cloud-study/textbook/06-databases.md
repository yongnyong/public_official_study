# 6장. DB·복제·캐시

[목차](README.md) · 다음: [서버리스](07-serverless.md)

## 1. 먼저 질의를 써보기

서비스 선택 전에 다음 질문을 적는다. 무엇을 저장하는가? 어떤 키로 읽는가? 관계를 결합해야 하는가? 쓰기 후 즉시 최신 결과가 필요한가? 거래 여러 단계를 함께 성공·실패시켜야 하는가?

모델 요청 이력 예시: `request_id`, `model_version`, `status`, `created_at`. '요청 ID로 한 건 조회'와 '월별 업종별 통계 계산'은 다른 접근 패턴이다. 하나의 DB에 모든 분석 요구를 무조건 몰아넣지 않는다.

## 2. RDS·Aurora

관계형 데이터와 SQL·트랜잭션이 필요한 경우 검토한다. 관리형 DB도 스키마, 인덱스, 비효율적 질의, 연결 관리까지 전부 자동 해결하지는 않는다.

예: 요청 ID 검색이 느리다면 인덱스와 실행 계획을 검토할 수 있다. 서버를 키우기 전에 전체 테이블 스캔을 반복하는지 확인한다. 인덱스는 조회에 도움이 되지만 저장 공간과 쓰기 유지 비용을 갖는다.

## 3. Multi-AZ와 읽기 복제본

전통적인 RDS Multi-AZ **DB 인스턴스** 배포의 대기 인스턴스는 읽기 트래픽 분산 대상이 아니다. 장애 전환 목적과 연결한다. 반면 Multi-AZ **DB 클러스터**는 읽기 가능한 인스턴스가 있는 구조이므로 이름만 보고 일반화하지 않는다.

읽기 복제본은 읽기 부하 분산에 검토하며 비동기 복제 지연을 고려한다. 방금 쓴 내용을 즉시 읽어야 하는 경로를 지연 가능한 읽기 경로와 구분한다. 복제본을 추가해도 원본 DB의 모든 쓰기 병목이 해결되지는 않는다.

## 4. 연결 폭증과 RDS Proxy

함수나 서버가 동시에 많이 실행되면 DB 연결 수가 급증할 수 있다. 프록시는 연결 관리 부담을 줄이는 선택지다. 그러나 느린 SQL 자체를 빠르게 바꾸거나 데이터 모델 오류를 고쳐주는 것은 아니다.

조사 순서: 연결 수 → 실행 중 질의 → 락·대기 → CPU·메모리·I/O → 애플리케이션 연결 재사용.

## 5. DynamoDB 키 설계

파티션 키는 데이터를 분산하고 조회하는 데 중요하다. 모든 요청에 같은 키 값을 사용하면 특정 위치에 부하가 몰릴 수 있다. 높은 처리량이라는 서비스 특성이 잘못된 키 설계를 무조건 상쇄하지는 않는다.

예: 사용자별 요청 이력이라면 사용자 ID와 시간·요청 ID를 조합한 접근 패턴을 설계할 수 있다. 다만 특정 사용자 하나에 부하가 집중될 가능성, 범위 조회, 보조 인덱스 요구를 함께 살핀다.

Query와 Scan을 구분한다. Query는 키 조건 기반 접근이며 Scan은 더 넓게 데이터를 읽는다. 필터가 있다는 사실만으로 읽는 데이터가 항상 크게 줄어드는 것은 아니다. 일관성 옵션은 테이블·인덱스 등 대상에 따라 다르므로 문서를 확인한다.

## 6. 캐시 패턴

Cache-aside 예시:

1. 요청 키로 캐시를 확인한다.
2. 있으면 반환한다.
3. 없으면 DB를 조회한다.
4. 결과를 캐시에 저장하고 반환한다.

TTL이 길면 원본 변경을 늦게 반영할 수 있다. 너무 짧으면 캐시 효율이 낮아질 수 있다. 같은 순간 캐시가 만료되면 DB 요청이 몰리는 문제도 고려한다. 민감정보 캐싱은 접근 통제와 보관 시간을 따로 설계한다.

모델 결과 캐시에는 입력뿐 아니라 모델 버전도 키에 포함하는 편이 필요할 수 있다. 버전 A의 답을 B의 답처럼 반환하면 결과가 틀릴 수 있기 때문이다.

## 확인 질문

- 읽기 복제본이 최신 값을 즉시 보장하는가? → 비동기 복제에서는 지연을 고려한다.
- 캐시를 추가하면 원본 DB가 필요 없어지는가? → 캐시 역할과 영속 원본 역할을 구분한다.
- NoSQL이면 데이터 설계가 불필요한가? → 접근 패턴·키·분산 설계가 중요하다.
