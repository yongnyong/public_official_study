# 2장. IAM·암호화·보안 설계

[목차](README.md) · 다음: [네트워크](03-network.md)

## 1. 인증과 인가

인증은 누구인지를 확인하고, 인가는 어떤 작업을 허용할지 판단한다. 출입증이 유효해도 모든 방에 들어갈 수 없는 것과 같다. AWS 접근을 설계할 때는 사람과 실행 프로그램을 구분한다.

- 사람: 조직의 로그인 체계·IAM Identity Center·역할 등을 검토한다.
- 워크로드: EC2 역할, Lambda 실행 역할 등 임시 자격 증명을 활용한다.
- 루트 계정: 필요한 계정 수준 작업에 제한해 사용하고 MFA를 구성한다.

장기 액세스 키를 코드에 넣으면 유출과 교체가 어려워진다. 역할 사용은 키를 코드에서 관리하는 부담을 줄이지만 역할 자체의 권한도 최소화해야 한다.

## 2. 정책을 문장처럼 읽기

아래는 예제 버킷의 한 경로에서 객체를 읽는 identity policy 예시다. 실제로 적용한 정책이 아니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-study-models/models/*"
  }]
}
```

읽는 순서: `Effect`는 허용/거부, `Action`은 작업, `Resource`는 대상이다. 이 정책만으로 객체 목록 조회나 삭제가 허용되지는 않는다. 목록 조회는 `s3:ListBucket`처럼 별도 작업이며 버킷 ARN을 대상으로 한다.

버킷 정책은 리소스에 붙는 정책이다. 역할 trust policy는 누가 그 역할을 맡을 수 있는지를 정한다. 역할을 맡을 수 있다는 사실과 그 역할로 어떤 API 작업이 가능한지는 구분한다.

## 3. 권한 오류 분석 순서

1. 실제 요청 주체가 예상한 역할인지 확인한다.
2. 호출한 작업과 대상 ARN을 확인한다.
3. identity policy와 resource policy를 확인한다.
4. 명시적 거부, 조건, 권한 경계, 조직 SCP 등을 확인한다.
5. 암호화 키 권한 등 추가 의존성을 확인한다.

SCP는 조직 내 권한의 상한을 제한하는 수단이며 그 자체로 사용자에게 권한을 부여하지 않는다. 'SCP에서 허용했으니 모든 작업이 가능하다'는 결론은 틀리다. 계정 간 접근은 양쪽 정책과 신뢰 관계를 함께 확인한다.

## 4. 암호화의 두 위치

저장 암호화는 디스크·객체 등 보관된 데이터를, 전송 암호화는 이동 중인 데이터를 보호한다. TLS를 켰다고 저장 데이터가 자동으로 모든 요구를 충족하는 것은 아니다.

KMS를 사용하는 경우 데이터 접근 권한과 키 사용 권한을 함께 설계한다. 봉투 암호화는 데이터를 암호화하는 키와 그 키를 보호하는 키를 나누어 생각하는 방식이다. 키를 사용할 수 없으면 암호화된 데이터 복구가 어려워질 수 있으므로 키 관리도 복구 계획의 일부다.

Secrets Manager는 DB 비밀번호 같은 비밀정보 관리와 관련된다. KMS는 암호화 키 관리 서비스다. 두 서비스를 같은 역할로 외우지 않는다. 비밀정보 회전은 연결된 애플리케이션이 새 값을 사용하도록 설계해야 효과가 있다.

## 5. 위협별 서비스 선택

| 요구 | 검토할 서비스·기능 | 구분 |
|---|---|---|
| 웹 요청의 악성 패턴 필터링 | WAF | IAM 권한 부여와 다름 |
| DDoS 방어 | Shield | SQL 질의 오류 수정과 다름 |
| 위협 신호 탐지 | GuardDuty | 모든 위협의 자동 해결을 의미하지 않음 |
| S3 민감정보 발견 | Macie | 일반 API 성능 모니터링과 다름 |
| 애플리케이션 사용자 인증 | Cognito | EC2 서버 역할과 다름 |
| 인증서 관리 | ACM | 암호화 키 정책 관리와 다름 |

## 6. AI 서비스에 적용하기

예측 API에는 공개할 수 있는 입력 인터페이스와 비공개 모델 저장소를 분리한다. 요청 로그에는 토큰·비밀번호를 남기지 않는다. 입력 파일을 받는다면 형식·크기·처리 시간을 제한하고 실행 가능한 임의 코드를 그대로 신뢰하지 않는다.

IAM 권한만으로 애플리케이션 수준의 입력 검증을 대신할 수 없다. 각 계층의 책임을 분리해 설계한다.

## 직접 답하기

Q. 서버가 모델을 읽을 수 있게 하려면 관리자 권한이 필요한가?

A. 아니다. 필요한 객체 읽기와 관련 키 사용 등 실제 작업에 맞춰 권한을 제한한다.

Q. 암호화하면 잘못된 권한 설정을 무시해도 되는가?

A. 아니다. 허가받은 주체가 복호화까지 가능하면 데이터에 접근할 수 있다. 권한과 암호화를 함께 설계한다.
