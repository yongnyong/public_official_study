# 8장. 관찰·재해복구·비용

[목차](README.md) · 다음: [사례](09-cases.md)

## 1. 무엇을 관찰할 것인가

서버 CPU 하나만으로 사용자 경험을 알 수 없다. 성공률, 응답 시간, 큐 적체, DB 연결, 저장 오류, 비용 증가를 요구사항에 맞게 관찰한다.

- 메트릭: 시간에 따른 숫자. 예: 분당 오류 수.
- 로그: 사건별 기록. 예: 요청 ID와 오류 내용.
- 추적: 여러 서비스에 걸친 요청 흐름과 지연.

CloudWatch는 운영 지표·로그·경보, CloudTrail은 API 활동 감사, Config는 자원 구성 기록·규칙 평가 관점에서 구분한다. API 실행 기록과 애플리케이션이 남기는 로그는 같지 않다.

## 2. 좋은 경보

'CPU가 높다'는 경보만 받으면 실제 사용자 영향이 불분명할 수 있다. 목표 지연 초과, 오류율 증가, 가장 오래된 작업 대기 시간처럼 서비스 목적과 연결되는 지표를 함께 사용한다.

모든 일시적 변동에 호출하면 경보를 무시하게 된다. 관찰 구간·임계값·담당자·첫 조치를 정한다. 경보 문서에는 대시보드 위치와 최근 배포 확인 절차를 포함한다.

## 3. RTO·RPO 계산

RTO는 장애 후 허용되는 복구 시간 목표다. RPO는 허용 가능한 데이터 손실을 시간으로 나타낸 목표다.

예: 14:00에 장애가 발생했다. 목표 RTO가 30분이면 14:30까지 복구하는 계획이 필요하다. 목표 RPO가 5분이면 최소 13:55 수준의 데이터까지 복원할 수 있도록 준비해야 한다.

매일 자정 백업만 있고 추가 기록이 없다면 오후 장애에서 5분 RPO를 충족할 수 없다. 백업 파일이 존재하는 것과 복원에 성공하는 것은 달라 실제 복구를 시험한다.

## 4. 재해복구 전략

| 전략 | 생각하는 구조 | 상대적 부담 |
|---|---|---|
| 백업·복원 | 장애 후 자원과 데이터 복원 | 평시 비용 낮을 수 있으나 복구 오래 걸릴 수 있음 |
| Pilot light | 핵심 부분을 유지하고 나머지 확장 | 핵심 데이터 동기화·확장 절차 중요 |
| Warm standby | 축소된 실행 환경 유지 | 빠른 확장을 위해 용량·할당량 확인 |
| 다중 사이트 활성 운영 | 여러 위치에서 실제 요청 처리 | 데이터 일관성·충돌·운영 복잡성 증가 |

각 전략의 실제 RTO/RPO는 구현과 테스트에 달려 있다. 이름만으로 수치를 보장하지 않는다. AZ 장애 대응과 Region 장애 대응의 범위도 구분한다.

## 5. 비용 계산 연습

다음은 **실제 AWS 요금이 아닌 가상 단가**다.

- 서버: 시간당 0.10 단위 × 100시간 = 10.
- 저장: GB·월당 0.02 단위 × 50GB = 1.
- 요청: 1,000회당 0.01 단위 × 20,000회 = 0.2.
- 전송: GB당 0.05 단위 × 10GB = 0.5.
- 합계: 11.7 단위. 세금·다른 항목은 제외한 예제다.

계산 순서는 단가 암기보다 **사용량 단위를 맞추는 것**이 중요하다. 실제 견적에서는 Region·저장 계층·교차 AZ/Region·인터넷 송신·NAT·로그 등도 검토한다.

## 6. 구매 방식 판단

온디맨드는 사용량 변동이 크거나 단기 실습일 때 검토하기 쉽다. Spot은 중단 가능성을 견딜 수 있는 작업에 검토한다. Savings Plans·Reserved Instances 같은 약정형 선택지는 꾸준한 수요와 조건을 비교한다. 할인이라는 단어만 보고 실습용으로 장기 약정을 구매하지 않는다.

오토스케일링은 최소·최대 용량과 지표가 잘못되면 비용 문제를 만들 수 있다. Budget 알림은 기본적으로 알림이며 모든 비용을 즉시 차단하는 상한이 아니다.

## 7. 실습 종료 점검

서버 중지와 삭제를 구분한다. 남은 볼륨·스냅샷·IP·로드 밸런서·로그·NAT·엔드포인트·DB가 있는지 확인한다. 데이터 삭제 전에 학습용 자원이 맞는지 식별한다. 실제 청구 정보는 지연될 수 있으므로 종료 직후 0으로 보인다고 확정하지 않는다.
